## Deviations from pre-registration

- Seeds: the registered design is 10 seeds per task per arm. Seeds complete over all 60 tasks: frozen 6, drift-1 0, drift-3 0. The arm matrix is incomplete, so case CWR-018 cannot pass on this campaign, and every interval above is over fewer Instances than registered.
- Missing and excluded cells are not missing at random. Cells that run to the turn limit take longest, so the cells still running when the campaign was stopped, and the cells whose model requests failed mid-run, over-represent long and failing Instances, most of all in the ablated arms. Every mean above is over the cells present and is likely biased toward success in those arms; the deltas against the control are therefore more likely understated than overstated.
- len basis: experiments.md 3.1 defines len as the reference solution's turn count. It was registered from benchmark/suite.kvx before any run, not re-measured from a frozen-arm run. 34 of 60 tasks have len 1 and 49 have their drift-1 injection at turn 1, so for them the drifted rule holds from the first turn: an undocumented rule rather than a mid-task change. Turns are max(1, floor(...)) because injections happen before a turn's script and turns start at 1.
- Drift specs: every injection is precondition_added from the fixed template table in benchmark/campaigns/h1h2.py, drawn per task by the registered seeded rule from the task's rules file. Some templates cannot be satisfied for some tasks, which turns the drift into an impossible task; results are therefore also reported per spec.
- Drift visibility: the drift grammar has no visibility key and the kernel writes every drift record with visible false, so the model's first evidence of a drift is a failure the manual does not predict.
- Build root: the campaign compiles refworld into .cwr/campaign-1/build (experimental Builds into the xbuild/ beside it) rather than build/, because build/ already held other refworld Builds of the same version, which the changelog gate refuses as a previous Build. The control Build therefore takes the first-Build path and its hash depends only on the World Source and the compiler.
- Frozen inputs: the campaign ran on copies of the task suite and of the suite cassette set taken at registration under .cwr/campaign-1/frozen; tests/cwr/cases/5_2.py verifies that their digests equal the registered suite and cassette digests.
- Pre-registration amendments, all made before any result of the executed campaign existed under benchmark/results: task 5.2 re-registered the metrics.py digest after task 5.3 added the H4 misuse scope (no H1 or H2 definition changed); the review of the task suite then re-froze the suite, suite cassette and upgrades digests ([deviation.suite_review_2026_11_06] in benchmark/preregistration.kvx: rules the starting state cannot trigger pruned, rate rules removed, adapter parameters pinned in task.md). benchmark/campaigns/h1.kvx and h2.kvx were regenerated from the re-frozen suite, so their drift specifications use its rules and turns and their registered_at precedes every attempt.
- Aborted executions: three earlier executions were stopped before completion and are retained outside the results tree (.cwr/campaign-1/aborted-1 to aborted-3), never analysed and never pooled. The first ran in one process whose Python threads were CPU-bound and was overtaken by the metrics.py change; the second was stopped within minutes when a suite revision was found; the third, run on the earlier suite and cassette digests, was stopped when the suite review re-froze them, because results under the earlier digests belong to the earlier registration.
- Harness: the pilot found that the predicate state view kept kv values in the kernel's bytes encoding, so no kv-based predicate could hold; task 5.2 patched that before the first registration and task 5.1 later replaced the mapping with benchmark/predicates/common.py state_view_from_instance, which the executed campaign uses. Every runner process records the sha256 of the harness sources it loaded in .cwr/campaign-1/runners.jsonl; the processes of the executed campaign loaded one version.
- Execution: runner processes of thirty workers each shared the cell list through per-cell locks. The first twelve spread their model requests over the first two gateway endpoints of .env; later passes, started to re-run cells whose runner had stopped or whose model requests failed, used both or, once the second endpoint answered 503, the first only. Every endpoint serves the one configured model identity with the same keys and no sampling parameter; the third answered 503 during an aborted execution and was not used. A cell's endpoint slot is recorded in its gateway.json, never the URL. Cells that ended in a model or kernel error were run again from a fresh Instance and the harness moved each failed attempt aside to benchmark/results/_replaced; cells in flight when a runner stopped left only staging directories, kept under .cwr/campaign-1/staging-leftovers and never analysed. Attempts moved aside for this hypothesis: 153.
- Instance stores: each worker thread uses its own Instance store under .cwr/campaign-1/home, so concurrent Instances of one task never share a file.
- Turns to success: analyse.py computes it by the registered stop rule (convention c7: the runner stops after the first turn whose predicate holds, so a successful Instance's last turn is its first satisfying turn), from an analysis view that holds each cell's ledger, final state and attempt record but not the recorded model messages. With the messages present analyse.py instead replays every turn, and a replay re-runs each script under the Build's 30000 ms wall-clock limit: on the loaded host a recorded turn that finished in time exceeded the limit when replayed (for example the first turn of h2/script/t060-report-pipeline/5), and analyse.py refuses the whole analysis on any such divergence. The method appears per arm and bin as turns_to_success_method.
- Host load (a threat): during the campaign other processes on the host drove the load average far above the core count, so the runner count was reduced. Turns that ended in LIMIT with no call record failing with LIMIT hit a turn budget (CPU, wall clock or memory; in the one-primitive arm also the primitive_calls budget, whose refused call writes no record): frozen 380, drift-1 620, drift-3 1266. Outside the one-primitive arm these are counted as recorded and may include turns the host load starved.
- Model identity: the gateway reports its own identity string, which every attempt record keeps as model_reported and the harness accepts under the registered routing_prefix rule.
- Replay condition (a threat, not a deviation): a model request that differs from the reference solution's recorded request is a cassette miss and returns UNAVAILABLE, in every arm alike; the re-frozen suite pins adapter parameters in task.md to limit this.
- The control arm of H1 (frozen) and of H2 (script) are the same Build and K; they are run and reported separately, as registered.
